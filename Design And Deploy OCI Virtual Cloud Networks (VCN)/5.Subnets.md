### **Subnet Types: Availability Domain-Specific vs. Regional**

*   We also discuss availability domains. And you can see that in this particular region, we have three availability domains.
*   Now a subnet can exist on an availability domain, the availability domain-specific, or you can have a regional subnet.
*   **Example VCN and Subnets:**
    *   The VCN is using an RFC 1918 recommendation. It's a 10.0.0.0/16.
    *   The subnets belong to that CIDR range:
        *   10.0.1.0/24 for subnet A
        *   10.0.2.0/24 for subnet B
        *   10.0.3.0/24 for subnet C
    *   The fourth subnet is a regional subnet.

*   **Availability Domain-Specific Subnet:**
    *   The availability domain that hosts subnet A when you create a resource will always be on availability domain 1.
    *   So any resource that you place on subnet A will always be on availability domain 1.
    *   That's an availability domain-specific subnet.

*   **Regional Subnet:**
    *   Any resource that you create on a regional subnet (like subnet D), you can allow OCI to select an availability domain, or you can specify what availability domain you want.
    *   You can go ahead and specifically select the availability domain for that regional subnet.

### **The Benefit of Regional Subnets for High Availability**

*   This is important because if an availability domain goes down, let's assume that availability domain 1 goes down:
    *   All the resources that you have on your subnet A (an AD-specific subnet) are going to be going down with that subnet because the availability domain is down.
    *   On a regional subnet (like subnet D), only the resources that reside on availability domain 1 are going to be going down.
    *   If you have a resource on the regional subnet that resides on availability domain 3, it is not affected by the failure in AD 1.
*   That's the benefit of having a regional subnet.
*   A regional subnet is what Oracle Cloud Infrastructure recommends as best practices for the reason that I just explained.
*   This is a unique characteristic from Oracle Cloud Infrastructure that you don't find in any other of the cloud service providers.

### **Key Characteristics and Rules for Subnets**

*   A VCN is divided into subnets. And you can have up to 30 subnets per virtual cloud network.
*   Each subnet has a continuous range of CIDR blocks. And you can have one or up to five CIDR blocks per subnet IPv4. And you can have the same for IPv6. IPv6 is optional.
*   Once you create your subnet and give it a CIDR range, you can increase that CIDR range or decrease it.
    *   **Example:** Subnet A is a /24. If you want to reduce the size because you're not going to be using all 256 addresses, you can reduce it to a /25 or a /26.
    *   You have the liberty of doing that. And then if you change your mind later on, you can always go back.
    *   You can shrink it as long as you don't have resources that are using the IP addresses in the portion of the range you want to reduce.

### **Placing Resources and IP Assignment**

*   Instances are placed on a subnet. You cannot have an instance of a compute node, a load balancer on the Virtual Cloud Network itself. You need to create a subnet to place that resource.
*   Each subnet can be public and private.
*   You can determine how the instance is going to be communicating outside of the VCN:
    *   If you have a public resource, then you need to place that public resource on a public subnet and assign it a public IP (which is optional).
    *   If you want to keep it private, then you need to assign that resource to a private subnet.
*   Private IPv4 addresses are assigned from the VCN's CIDR block into the instance's VNIC (Virtual Network Interface Card).
*   The public IP address is also assigned to the VNIC. And you can have up to 32 IP addresses, but we'll get into that when we see VNICs.
