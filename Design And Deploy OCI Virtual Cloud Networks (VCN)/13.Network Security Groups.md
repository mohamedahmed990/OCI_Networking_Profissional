### **Introduction to Network Security Groups (NSGs)**

*   Hello and welcome. I'm Sergio Castro at Oracle University. And today we are seeing a lesson on network security group.
*   If you might recall from the previous lesson on security lists, a security list is a set of firewall rules that are applicable at the **subnet level**. So every single resource at that subnet is bound by the security list.
*   The network security group is similar, but the rules apply to resources that have the **same security posture**.

### **NSGs vs. Security Lists: A Practical Example**

*   **Security List Example:** A VCN with three subnets, all bound by the same rule (e.g., port 80 enabled). Even if a resource is not a web server, port 80 is enabled on it.
*   **NSG Example:** A web server has a specific security posture. If you have two web servers, you can create an NSG to enable port 80 **only for those specific resources**, even if they are on different subnets.
*   You can have nodes on different subnets with a security list containing several rules. If port 80 is not enabled on the security list, you can enable it **only for the web servers** using an NSG.

### **Key Characteristics of Network Security Groups**

*   They consist of rules that apply only to a **set of VNICs** that you choose.
*   They are not limited to compute instances. NSGs can be applied to:
    *   Load Balancers
    *   Database Systems
    *   Autonomous Database
    *   Mount Targets
    *   And many other resources.
*   **Oracle recommends using NSGs over security lists** because they offer more granular control.

### **How NSGs and Security Lists Work Together**

*   A subnet **must** have a security list. You can use them in combination with NSGs.
*   You can have a security list with broad rules and then use NSGs to apply granular rules to specific resources.
*   The rules that apply to a given VNIC are the **union (combination)** of the rules from:
    *   All security lists associated with its subnet.
    *   All network security groups associated with the VNIC itself.
*   A packet will be allowed if it is permitted by **either** a security list rule **or** an NSG rule.

### **Visual Example: Using NSGs Across Subnets**

*   **Scenario:**
    *   **NSG A:** Has a stateful ingress rule allowing port 80 (HTTP).
    *   **NSG B:** Has a stateful ingress rule allowing port 22 (SSH).
*   **Deployment:**
    *   Subnet A has two instances: one bound by **NSG A**, the other by **NSG B**.
    *   Subnet B has an instance bound by **NSG A**.
*   This creates a redundant web server setup where the web servers (bound by NSG A) can be in different subnets for high availability.
*   The security lists for the subnets can have their own rules, but the NSG rules provide specific, targeted access.

### **Important Differences and Limits**

#### **Rule Limits**
*   **Security Lists:** A subnet can have up to **5** security lists. Each list has a hard limit of **200 ingress** and **200 egress** rules.
*   **Network Security Groups:** The same limits apply per NSG (200 ingress, 200 egress).

#### **A Key Functional Difference: Source/Destination in Rules**
*   **Security List Rule Source/Destination:** Can only be a **CIDR block** (e.g., `10.0.0.0/24`) or an **Oracle Service**.
*   **NSG Rule Source/Destination:** Can be another **Network Security Group**. This allows you to create rules based on security group membership, enabling complex, nested security policies.

#### **Stateful vs. Stateless Rules**
*   The same concepts of **stateful** and **stateless** rules apply to NSGs as they do to security lists.
*   **Stateful (Default):** You only need to specify the rule in one direction (e.g., ingress). The return traffic is automatically allowed.
*   **Stateless:** You **must** configure matching ingress and egress rules for the connection to work. This is used for very specific, high-performance scenarios like load balancing or big data.

### **Provisioning and Configuration**

*   **Security Lists:** A default security list is **automatically created** when you create a VCN.
*   **Network Security Groups:** You must **create and configure every NSG from scratch**. A new VCN starts with zero NSGs.

### **Summary of Rule Configuration**

*   **Example Stateful Ingress Rule (Web Server):**
    *   **Source:** `0.0.0.0/0` (The open internet)
    *   **IP Protocol:** TCP
    *   **Source Port:** (Typically ephemeral)
    *   **Destination Port:** 80
*   **For a Stateless Rule:** You must also create a matching egress rule where the source port is 80 and the destination port is ephemeral for the return traffic.
